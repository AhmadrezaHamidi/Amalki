# تست بار با k6

اسکریپت‌های [k6](https://k6.io) برای سنجش کارایی سایت زیر بار. هر سه اسکریپت فقط می‌خوانند (چیزی منتشر یا حذف نمی‌کنند)، پس روی دیتابیس مشترک هم بی‌خطرند.

| فایل | چه چیزی را می‌سنجد | آستانهٔ قبولی (p95) |
|---|---|---|
| [public.js](public.js) | بازدیدکننده: خانه ← فهرست با فیلتر تصادفی (شهر، نوع، متراژ، خواب، مرتب‌سازی، صفحهٔ ۲ تا ۶) ← جزئیات آگهی | خانه ۴۰۰ms، فهرست ۵۰۰ms، جزئیات ۴۰۰ms، خطا زیر ۱٪ |
| [seo.js](seo.js) | خزنده‌ها: `sitemap.xml`، `llms.txt`، `robots.txt` با نرخ ثابت | سایت‌مپ ۲s، llms ۳۰۰ms، robots ۱۰۰ms |
| [admin.js](admin.js) | مدیر: ورود یک‌باره، داشبورد، فهرست آگهی‌ها، فرم ویرایش، سرنخ‌ها، تیکت‌ها | فهرست ۱.۵s، بقیه ۵۰۰ms |
| [seed.sql](seed.sql) | دادهٔ حجیم نمونه: N آگهی (پیش‌فرض ۲۰٬۰۰۰، یک‌دهم پیش‌نویس) با ۵ عکس برای هر کدام | — |
| [lib.js](lib.js) | نشانی‌ها، کمک‌تابع‌ها و پروفایل‌های بار | — |

## اجرا

```bash
# ۱. داده: دیتابیس با migrationها ساخته شده باشد، بعد
sqlcmd -I -S localhost -U sa -P '<pw>' -d Amlak -v Listings=20000 -i loadtest/seed.sql

# ۲. سایت را در حالت Production بالا بیاورید (Development کندتر است و نتیجه را خراب می‌کند)
ASPNETCORE_ENVIRONMENT=Production dotnet run --project src/Amlak.Web -c Release --no-launch-profile --urls http://localhost:5244

# ۳. تست‌ها
k6 run loadtest/public.js                                   # بار عادی: ۵۰ کاربر هم‌زمان، ۳ دقیقه
k6 run -e PROFILE=smoke loadtest/public.js                  # دود: ۱ کاربر، ۳۰ ثانیه
k6 run -e PROFILE=stress -e VUS=50 loadtest/public.js       # فشار: ۵۰ ← ۱۰۰ ← ۲۰۰ کاربر
k6 run -e RATE=1 loadtest/seo.js                            # ۱ سایت‌مپ و ۵ llms/robots در ثانیه
k6 run -e ADMIN_EMAIL=... -e ADMIN_PASSWORD=... loadtest/admin.js   # ۵ مدیر هم‌زمان
```

متغیرها: `BASE_URL` (پیش‌فرض `http://localhost:5244`)، `PROFILE` (`smoke`، `load`، `stress`)، `VUS`، `THINK` (مکث بین کلیک‌ها به ثانیه، پیش‌فرض ۱)، `RATE` و `DURATION` برای seo.js.

نکته‌ها: k6 کوکی‌ها را در هر تکرار پاک می‌کند؛ admin.js با `noCookiesReset` ورود را نگه می‌دارد و پاسخی را که به صفحهٔ ورود برگردد خطا می‌شمارد. شمارهٔ فرضی ۵۰ کاربر هم‌زمان با مکث ۱ ثانیه حدود ۶۰ درخواست صفحه در ثانیه است، یعنی چند صد هزار بازدید در روز.

## نتیجه‌ها (۲۰۲۶-۱۰-۲۶)

محیط: یک ماشین ۴ هسته‌ای با ۱۵ گیگ حافظه، SQL Server 2022 و سایت (‏.NET 9، Production) و k6 همه روی همان ماشین. ۲۰٬۰۰۰ آگهی و ۱۰۰٬۰۰۰ عکس. سرور واقعی کندتر یا تندتر باشد عددها جابه‌جا می‌شوند، ولی نسبت‌ها و گلوگاه‌ها همین‌اند.

### بازدیدکننده (public.js، ۵۰ کاربر، ۴ دقیقه)

| نسخه | خانه p95 | فهرست p95 | جزئیات p95 | درخواست در ثانیه | خطا |
|---|---|---|---|---|---|
| پیش از output cache | ۲۳.۷s | ۲۲.۵s | ۱۹.۴s | ۲.۹ | ۰٪ |
| main با output cache (PR #5) | ۲ms | ۱۲.۱s | ۱۲.۳s | ۸.۷ | ۰٪ |
| شاخهٔ CQRS (PR #12) | ۱ms | ۲۴ms | ۶ms | ۶۰.۸ | ۰٪ |

- **گلوگاه اصلی:** هر کوئری با `Include(p => p.Photos.OrderBy(x => x.SortOrder).Take(1))` (خانه، فهرست، «آگهی‌های مشابه» در جزئیات، فهرست ادمین) در SQL به `ROW_NUMBER() OVER (PARTITION BY PropertyId)` روی **کل جدول عکس‌ها** تبدیل می‌شود. با ۱۰۰ هزار عکس هر بار حدود ۴۵۰ms فقط برای یک کاربر طول می‌کشد و با تعداد عکس‌ها بزرگ‌تر می‌شود. همان کوئری با `OUTER APPLY (SELECT TOP 1 …)` ۹ms است. با ۵۰ کاربر CPU دیتابیس پر می‌شود و همه‌چیز صف می‌کشد.
- output cache صفحه‌های تکراری (خانه، robots، سایت‌مپ) را حل کرد، ولی فهرست با ترکیب‌های مختلف فیلتر و ۱۸ هزار صفحهٔ جزئیات بیشتر cache miss هستند و همان کوئری کند را اجرا می‌کنند.
- شاخهٔ CQRS (view کارت با `OUTER APPLY` و ایندکس `PropertyPhotos(PropertyId, SortOrder)`) همهٔ آستانه‌ها را با فاصلهٔ زیاد پاس می‌کند؛ ۶۰ درخواست در ثانیه سقف خودِ سناریو (۵۰ کاربر با مکث ۱ ثانیه) است، نه سقف سرور.

### خزنده‌ها (seo.js، ۱ سایت‌مپ و ۵ llms/robots در ثانیه، ۱ دقیقه)

| نسخه | sitemap p95 | llms p95 | robots p95 | تکرارهای جاافتاده |
|---|---|---|---|---|
| پیش از output cache | ۲۱.۷s | ۱۶.۵s | ۷ms | ۷۴ |
| main با output cache | ۱۲۳ms | ۱ms | ۱ms | ۰ |

سایت‌مپ هنوز همهٔ آگهی‌های منتشرشده را با همهٔ عکس‌ها بار می‌کند (اولین درخواست پس از هر تغییر آگهی حدود ۳ تا ۵ ثانیه). با cache قابل قبول است، چون فقط بعد از ذخیرهٔ آگهی دوباره ساخته می‌شود.

### مدیر (admin.js، ۵ مدیر، ۴ دقیقه)

| صفحه | پیش از این PR p95 | با صفحه‌بندی (این PR) p95 |
|---|---|---|
| فهرست آگهی‌ها | ۷.۵s (صفحهٔ ۴۶ مگابایتی) | ۶۸ms (۱۲۴ کیلوبایت، ۵۰ آگهی در صفحه) |
| داشبورد | ۳۹ms | ۶۰ms |
| فرم ویرایش | ۴۳ms | ۹ms |
| سرنخ‌ها / تیکت‌ها | ۱۴ms / ۱۳ms | ۱۴ms / ۱۳ms |

فهرست آگهی‌های ادمین همهٔ ۲۰ هزار آگهی را در یک صفحه می‌ساخت. حالا ۵۰ تا در هر صفحه است و عکس جلد با یک کوئری جدا روی همان ۵۰ آگهی خوانده می‌شود.
